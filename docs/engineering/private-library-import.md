# Private library imports

Private storage, consent, immutable task selection, isolated caching and provider staging are implemented. Provider activation remains unsupported pending native conformance evidence and a verified ready binding. No import writes `skill`, `skill_file`, or an agent's catalog bindings. Existing catalog import permissions remain unchanged.

The portable entry field names, content framing, canonical JSON, and golden vectors are pinned to the shared-library v1 model at revision `3b1cba3cd` (registry change #49). `server/pkg/libraryimport/testdata/entry-v1.json` is the portable manifest fixture. The adapter reuses `knowledge.ContentHash` for exact declarative text and `skillbundle.BuildManifest` for the separate immutable transport hash. Destination object IDs are allocated independently of source entry IDs. Origin authority/source/entry identity is retained; source provenance never grants destination access or execution permission.

## Consent and transfer

Consumers build a local `libraryimport.Preview`, display its destination server ID/origin, Workspace, owner, audience, entry identity/hash, every relative file path/hash/byte count, total bytes, exclusions, Project, optional persona tuple, runtime and exact task. Only after human confirmation of that exact digest may they call `Confirm` and `Upload`. Registration, inspection, and source load approval do not confirm transfer. No automatic uploader or background inventory disclosure is installed.

`Upload` freezes and validates the request locally, makes a metadata-free authenticated capabilities request, and checks the complete destination before POST. It disables redirects and checks that the receipt binds a valid destination object ID to the transport hash derived from the exact uploaded bytes. Cancellation, absent/expired consent, unavailable private storage, and destination changes prevent upload. Receipts expire after 15 minutes and authorize one attempt. Changing any disclosed field requires confirmation again. The request has a 16 MiB serialized limit and the existing lower 1 MiB/file, 8 MiB/entry and 256-file limits. Unsupported kinds, formats, execution requirements, ambiguous JSON, case-folded aliases, unsafe paths and changed bytes are rejected as a whole. Managed bundles fail with `policy_unavailable`; no managed-policy resolver is implied.

The server must have an explicitly configured stable `MULTICA_PRIVATE_IMPORT_AUTHORITY_ID`, a canonical `MULTICA_PUBLIC_URL` (HTTPS, or HTTP loopback for local use), and all storage migrations/indexes ready. Otherwise capabilities reports `private_import_unsupported` and POST rejects before reading a body. Identity is configuration-owned, never derived from request host headers. Clients must preflight; direct POST cannot retract bytes a caller has already sent.

## API and transaction

- `GET /api/private-library/capabilities`: human membership, no file metadata in the request.
- `POST /api/private-library/imports`: exact local consent receipt, immutable payload, and explicit binding; returns a storage receipt.
- `GET /api/private-library/imports/{id}`: owner-only complete object, including its retained selection and the existing bundle wire shape.
- `DELETE /api/private-library/imports/{id}`: human owner only, with a separately confirmed `RemovalRequest`. Display the removal operation, destination object and original preview (destination and every file) before `ConfirmRemoval`; prior import consent cannot authorize removal. The removal digest includes the complete displayed preview, object ID and operation, and expires after 15 minutes.
- `GET /api/private-library/tasks/{taskId}/imports/{id}`: existing task token for that exact invocation, with middleware-stamped task, persona, owner and Workspace identity. Broad daemon credentials do not grant private access. Other members, Workspace administrators, other tasks, broad daemon tokens and other Workspaces receive no private content.

New imports require a queued issue/chat task without an established session or knowledge snapshot, matching the explicit Project. The human must own its runtime and native persona and be its recorded originator or accountable human. An optional persona reference is `(serverId, workspaceId, personaId)` and must match the task's native agent ID; a daemon profile is never a persona ID. Other task origins fail closed in this milestone. An offline runtime may retain an inert import; this does not make it runnable.

A transaction fences Workspace deletion, locks membership, then runtime, persona and Project dependencies before locking and revalidating the task, enforces the combined 64-binding limit, and commits the complete private object once. Duplicate `(Workspace, owner, attempt)` requests return the original receipt when their complete preview digest matches, including after dispatch. A changed digest conflicts. Failed/interrupted transactions publish no object. Task reads and claim selection revalidate the current issue/chat Project against the consented Project and reject moved bindings. Owner reads retain historical access. Reads return the retained bytes and verify both hashes; they never rescan sources. Consent expiry does not erase historical objects or grant new uses. Owner removal atomically wipes the payload and retains a metadata-only removal record while the task exists, so delayed retries of the original attempt return `410 private_import_removed` rather than recreating content. Task reads, claims and cache reauthorization deny removed objects; retained child manifests stay immutable and cannot restore access. A running provider cannot be made to forget bytes it already received.

Issue deletion captures task IDs under its deletion fence, cascades the task deletion, then removes their now-unreferenced imports in the same transaction. Sweeping after the cascade catches imports that committed while deletion waited on a task lock. A bounded hourly reaper also removes pre-existing orphans and imports orphaned by other task/agent cascades, using batches of 500, at most 20 batches per run, and skipping locked rows. A terminal task remains a valid retention owner; losing a runtime, persona binding, Project or membership alone does not silently erase retained owner history. Explicit owner removal can revoke a retained object. Workspace deletion removes these server-owned rows; no external file is touched. The nullable `removed_at` addition is metadata-only and requires no new index or table rewrite.

## Claim, resume and private cache

Storage receipts report `stored` and `unsupported_provider`. `approvalRef` acknowledges consent to store the exact digest under the destination authority; it is not a load/invocation grant. There is no publication endpoint, shared catalog fallback, Project-wide discovery, provider readiness, or reload in this milestone. Destination policy and load approval must be checked again before any future protected use.

Claims persist a private child manifest with compare-and-set semantics, including an explicit empty selection, bound to the existing knowledge/context digest. Its destination, Project, native persona, exact task/runtime, provider, adapter revision, consent digest, and portable/transport hashes are immutable. A separate Project-context digest covers title, description, instructions, execution-resource pointers and the pinned knowledge digest; changes refuse reuse rather than rewriting the retained child. Adding an import after either context is pinned is refused. Owner membership and current runtime/persona ownership are checked again. Private import/claim transactions reject aggregate selections above 8 MiB or 1,024 files before loading the payload set. The new nullable JSONB column is an additive, metadata-only migration without a table rewrite or new index; session reconstruction uses the existing knowledge-session index.

A retry of the same invocation retains its child manifest and bytes. A different task cannot inherit the prior task's private access by resuming its session. Resume, retry and rerun successors need explicit authorization for their own invocation; changing content requires a new task and fresh session. No source rescan, shared-catalog fallback or automatic re-import occurs.

The daemon downloads with the exact task token and disables redirects. Private bundles reuse transport verification and cache locking but use a separate owner-restricted cache (0700 directories, 0600 files, atomic file replacement without recursive directory deletion). Its hashed namespace binds the complete selection digest and provider version; that selection covers authority/origin, Workspace/owner, Project/context revision, invocation/snapshot, provider/adapter and approval digests. Unix directory permissions are verified before transfer. Windows private caching remains unsupported until an owner-only ACL implementation is available; mode bits alone cannot establish that boundary. Controller availability is not cached. Every cache hit performs an authenticated HEAD check against the current server ownership and membership gates and checks both hashes and the approval digest. Offline or denied authorization blocks use of retained bytes. Combined context limits include local knowledge, existing skills and imported files, with a 64 KiB standing-guidance limit.

## Provider staging and activation gate

The Claude text-skill staging adapter verifies the native frontmatter name, preserves every approved byte, writes read-only files, and returns the actual canonical path and ownership generation. It rejects unsupported frontmatter, hooks, executable preprocessing, same-name commands, and native-name collisions. Finding a suffix directory never authorizes rewriting immutable frontmatter or advertising an inferred invocation. Rules use the existing Project context layer, preserve exact text and do not change instruction precedence. Only ready returned bindings can enter the runtime listing or active rule composition.

Capabilities explicitly report `taskActivation=unsupported_provider`, `taskActivationReason=native_conformance_missing` and `reload=unsupported`. The default provider gate refuses before preparation or launch. Staging fixtures prove placement, integrity, rollback and returned binding metadata; they are not native-provider evidence. No entry becomes ready, and no live provider call is made by these tests. Activation remains unfinished until version-specific evidence proves the actual resolved file/content and competing native lookup behavior, and the runtime binding is confirmed against that evidence. A version label alone cannot enable loading. Storage consent does not substitute for destination load authorization. Codex task-home loading, prompt commands, role conversion, hooks and live selection replacement remain unsupported.

## Ownership and cleanup

Sidecar rollback and reuse now require a random ownership generation, filesystem and ancestor identities, and a baseline byte hash, size, mode and modification time. Unix regular-file identity includes change time so restoring modification timestamps cannot recreate the original ownership evidence. Manifests are atomically replaced with owner-only permissions to protect private path metadata. Exclusive creation prevents overwriting existing entries. Cleanup retains edited, newly added, replaced, symlinked, or legacy-unverifiable entries, returns their conflicts and retains the manifest. Only unchanged owned files and empty owned directories are reclaimed. Reuse declines a conflicted environment rather than deleting whole skill directories. Existing task markers are not overwritten or adopted as newly owned sidecars. The production activation gate prevents private provider loading until the release evidence is available.

DB-backed API/transaction tests are compiled separately and require an isolated migrated Postgres to execute. No live server is necessary for manifest, consent, preflight, cancellation, redirect, and transport tests.
