# Project knowledge references

Projects accept three additional `resource_type` values: `knowledge_file`, `knowledge_folder`, and `knowledge_skill`. They are text knowledge links. `github_repo` and `local_directory` retain their execution-resource behavior. Knowledge never selects a working directory, runs an attachment, installs a native skill, enables hooks, or uploads source bytes. Remote import and native skill invocation remain separate operations.

## Registration and API

On the source machine, use the intended configuration profile and an explicit canonical path:

```sh
multica --profile research --workspace-id <workspace-id> knowledge register file /absolute/canonical/notes.md --owner-id <runtime-owner-user-id> --allow-read --approve-context
multica --profile research --workspace-id <workspace-id> knowledge register folder /absolute/canonical/reference --owner-id <runtime-owner-user-id> --allow-read --approve-context
multica --profile research --workspace-id <workspace-id> knowledge register skill /absolute/canonical/skill --owner-id <runtime-owner-user-id> --allow-read --approve-context
```

Both flags are required: one permits bounded local inspection, the other authorizes the inspected digest for text context. Registration is unavailable from a managed task. The command makes no network request and emits only `resource_type` and `resource_ref`. Inspect the selected local content before granting context approval. Attach the returned reference explicitly with `multica project resource add <project-id> --type <resource-type> --ref '<resource_ref-json>'`, or the existing Project resource API. Only that metadata is sent. Registration itself does not attach anything.

The API supports these types in bundled Project creation and resource create/update. Binding a reference requires the authenticated human owner and a runtime owned by that user on the stated daemon in the selected workspace. Task and cloud-node credentials cannot attach or rebind knowledge on behalf of that owner. The runtime may be offline while saving a reference. A claim on an unavailable or different machine fails visibly; the server never substitutes a same-named path on another machine. Project resources remain workspace-scoped. Existing clients can render unknown resource types through their generic resource fallback; shared clients validate the new metadata.

A reference carries schema version, owner, daemon/resolver identity, opaque root and root generation, authority/source/entry identity, source revision, format, entry point, and content hash. Absolute locators and filesystem identity remain in the owning profile's `knowledge-v1/sources` directory. References contain no local path or file bytes. Renaming an external path produces a new candidate; there is no inferred move. Re-registering an explicitly selected existing locator preserves its source/entry IDs, increments the source revision for changed content, and increments root generation on target replacement. Registrations are serialized with an OS lock. Different roots retain different identities even when their content matches.

Skill references use opaque independent authority/source/entry IDs and the shared-library v1 content-hash framing: `shared-library-entry-v1`, kind `skill`, format `native-skill-text-v1`, `SKILL.md`, sorted exact text-file paths/modes/byte lengths/SHA-256 values, then zero requirements. The hash is distinct from Multica's existing skill-bundle transport hash. No frontmatter or supporting-file rewriting occurs. Shared-library golden vectors cover the framing. These are knowledge-only references; unsupported executable files are rejected, and no native invocation readiness is asserted.

## Claim, snapshots, and resolution

The shared issue/chat/autopilot/quick-create claim resolver partitions knowledge from execution resources. Immediately before dispatch, the server pins an ordered `knowledge_manifest` on the task with an atomic first-writer update. The selection includes workspace, Project, owner, daemon, snapshot ID, bindings, and a digest. Reclaims choose the stored winner. A resumed provider session inherits its earlier selection through the same agent's session identity. Current runtime ownership, workspace membership, resolver identity and the request's `knowledge-context-v1` capability are checked again. Unsupported daemons fail the task with a persisted visible reason, including after a downgrade. Empty selections preserve existing execution behavior.

Before preparing the runtime, the owning daemon resolves the selection through its profile-local registry. It checks the server, workspace, owner, daemon, complete reference, root identity, exact content hash and aggregate context budget. An unavailable remote source never triggers an upload, download, mount, path substitution, or shared-catalog publication.

Successful resolution publishes an immutable local snapshot atomically, keyed by server and snapshot ID, outside provider discovery paths. Retries and resumed sessions verify and reuse the saved bytes. Changed, deleted, detached or missing sources cannot rewrite that session. A new session using changed/missing content fails until the user explicitly registers and binds an approved revision. Corrupt, mismatched or missing retained snapshots fail; a durable commit receipt prevents reconstructing a published snapshot from live files. Per-snapshot OS locks serialize preparation and release automatically after a process exits.

Runtime context embeds the verified text snapshot in `.multica/project/resources.json`, under `knowledge`, separately from `resources`. The runtime brief identifies the snapshot and digest. A pre-existing sidecar collision in a local execution directory fails preparation instead of omitting knowledge. A resumed workdir whose knowledge projection fails is declined for reuse and must pass fresh preparation before execution. Projection uses directory handles, rejects symlink/special-file targets and requests owner-only file permissions (`0600`; Windows uses inherited filesystem ACLs). Original sources are read-only inputs; no executable or native discovery files are written from them.

Bounds: 64 sources per owner and 64 selected knowledge bindings; four directory levels and 4,096 visited nodes; 1 MiB per file; 256 files and 8 MiB per entry; 1,024 files and 8 MiB across knowledge plus task guidance. Paths are canonical relative POSIX/NFC paths, at most 16 segments and 1,024 UTF-8 bytes, with case-fold collisions rejected. Text must be UTF-8 without NUL. Reads are bounded; symlinks, special files, executable files, root replacement and read-time replacement fail. Inspection and snapshot preparation have cancellable five/30-second budgets; no partial snapshot is published.

The daemon waits for knowledge resolution through a cancellable boundary with a 30-second deadline that includes waiting for capacity. If a filesystem syscall stalls, cancellation releases the task's preparation caller and discards any late result. At most two resolutions per daemon may remain in flight; each holds its permit until the underlying operation actually returns. Further resolutions wait within their own deadlines, so retries cannot accumulate abandoned reads. A permanently stalled filesystem can exhaust this capacity until it recovers or the daemon restarts.

Snapshots live in the owning profile's `knowledge-v1/snapshots` store and are retained independently of detachable links and transient task workdirs. This change performs no automatic snapshot garbage collection or source deletion. The existing task-context sidecar ownership lifecycle handles projected context files.

## Migration and verification

Migration 592 follows 591 and adds nullable `agent_task_queue.knowledge_manifest`. It creates no index, so there is no concurrent-index cleanup entry; that classification is recorded in the migration runner. Migration 593 adds the session lookup index in one concurrent statement, with invalid-index cleanup registered in the runner. Its rollback drops only that index concurrently. Workspace deletion already deletes task rows and Project resource rows; the deletion manifest explicitly classifies the new column and reference types with their containing rows. External files and local snapshots are never deleted by a server-side detach or workspace delete. Rolling back removes the manifest column; reconcile tasks that use knowledge before downgrading the server.

Focused coverage includes shared-library hash vectors, exact identity/revision behavior, scope denial, retained snapshots after edits/deletion, root replacement, symlink escape, FIFO/nonblocking reads, path conflicts, limits, concurrent snapshot publication, tampering, daemon resolution and context-only projection. DB-backed tests cover API ownership, cross-workspace rows, atomic pinning, claims, deletion and retained selection. Handler tests need migrated Postgres and skip the whole package without it; compilation alone does not validate those database behaviors.
